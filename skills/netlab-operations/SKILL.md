# Netlab 底座操作

通过平台现有 UI 或公共 API 完成操作，以任务结果和实际运行状态交付。保留用户指定的场景、资产、业务数据及网络关系。

## 确定操作对象

1. 从用户请求、当前会话和平台查询确定控制面地址、环境 ID、资产 ID、镜像来源及目标状态。沿用已明确的选择；同名对象使用 ID 区分。
2. 读取目标环境配置、运行状态和进行中的任务，再制定本次操作。已有 SSH、浏览器登录或 Service Token 按当前授权使用。
3. 涉及数据替换时，区分用户要的是初始模板、当前实例还是恢复点；仅在请求仍有歧义时询问。明确执行重建、覆盖或删除的对象及数据范围。

本技能不绑定服务器 IP、账号、场景名或发布版本。凭据通过当前会话或安全凭据渠道取得，输出与落盘记录省略敏感内容。

## 平台事实与契约

- Netlab 是独立控制面加 Linux 执行节点。Web 与外部调用方共用 `/api/v1`；REST 提交命令，SSE 通知环境变更，交互会话使用对应的流式或 WebSocket 接口。
- VM 使用 KVM/libvirt，容器使用 containerd/runc，网络使用 OVN/OVS。逻辑交换机、逻辑路由器由底座原生组网实现。
- 优先通过公共 API 操作资源和跟踪任务。SSH 用于授权范围内的文件传输、依赖准备及物理状态检查；生命周期操作继续走平台任务链。
- 有源码时，先核对仓库身份与目标版本，以 `api/openapi.yaml` 为请求契约，以 `internal/server/server.go`、相关 handler 和 `web/src/api/client.ts` 核对实际行为。源码仓库为 [scmypapa/netlab](https://github.com/scmypapa/netlab)。
- OpenAPI 的 `info.version` 是接口契约版本；平台安装版本通过系统更新接口读取。
- 服务端是授权和调度的执行入口。保持 ID、revision、任务 ID 的关联，通过平台修复操作冲突与资源引用；数据库写入、直接删除运行目录等操作不能代替平台执行链。

## 每次操作的闭环

1. **读现状**：目标配置、运行状态、活动任务、节点能力，以及本次所需的容量或引用关系。
2. **执行动作**：使用现有接口；一次逻辑操作使用一个稳定的 `clientRequestId`。原请求重试复用它，新意图使用新 ID。
3. **跟踪结果**：记录返回的任务 ID 或任务位置，跟踪阶段、数量和错误。HTTP 受理成功与物理执行完成分别判断。
4. **读回验证**：核对平台配置和实际状态。场景部署还需检查网卡、IP、路由、DNS及约定的业务入口。
5. **收尾**：释放临时会话，清理本次独有的中转文件；共享镜像、运行盘和恢复点依赖经平台确认后再清理。

遇到连接超时，先读取已提交任务和目标状态，确定动作是否已经生效。对可重试的失败使用平台重试入口；遇到确定性错误，定位阶段及对象后修正原因。避免重新创建一组并行任务。

## 本项目操作约定

- 保持已确定的资产数量、资源规格、原始名称、网卡顺序与网络隔离。资源不足时给出具体差额和可行调整，按用户选择执行。
- 环境重启保留运行数据；回到初始状态使用重建。镜像替换、实例更新与旧镜像清理是三个需要分别核对的结果。
- 主站和节点程序升级统一使用平台内置更新流程。首次安装及依赖准备按发布包正式安装流程执行。
- 发布新版本时，按当前用户约定先确认 README 和公告；本次已获明确豁免或确认时沿用授权。普通环境操作不触发代码发布。
- 用户未要求代码改动时，以配置、资源和运行事实完成任务；发现产品缺陷时说明根因及影响，再在授权范围内修复。

## 交付信息

用简体中文简洁列出：实际完成的对象和动作、任务与校验结果、仍需处理的具体事项。部署成功以实际检查为依据；明确区分镜像已导入、实例已更新、环境已启动和业务已验证。
